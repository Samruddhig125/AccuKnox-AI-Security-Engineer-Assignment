## 2. Key Architectural Components of an LLM Chatbot

When building an LLM chatbot from scratch, I look at it as a pipeline that takes a raw user message, enriches it with context, keeps it safe, and streams a grounded answer back.

### High-Level Flow
1. **Frontend & API Gateway:** Everything starts at the user interface (a web app or Slack/Teams bot) talking to a lightweight backend I usually go with **FastAPI** because async streaming works cleanly out of the box. This layer handles user authentication, session IDs, and basic rate limiting so one user cannot flood the backend.
2. **Input Guardrails:** Before the message touches the LLM, it passes through a quick filter to catch prompt injections, strip out sensitive PII, or block off-topic abuse.
3. **Orchestration Layer:** This is the traffic controller. Using frameworks like **LangGraph**, **LangChain**, or even plain Python for straightforward flows, it loads recent chat history from a session store (like Redis), decides whether the query needs external tools/APIs or a knowledge lookup, and assembles the final prompt.
4. **Knowledge & Retrieval Layer (RAG):** Instead of relying on the model's frozen training memory, domain documents are cleaned, chunked, converted into embeddings, and indexed. At query time, the orchestrator pulls the top-k relevant chunks (often combining keyword + semantic search) and injects them into the prompt—strictly filtering by the user's access permissions so private data doesn't leak across roles.
5. **The LLM Engine:** The assembled prompt goes to either a hosted API (Claude, GPT, or Groq for low latency) or a locally hosted open-weight model (via Ollama or vLLM) if strict data privacy requires keeping everything on-prem.
6. **Output Validation & Streaming:** As tokens generate, they stream back to the UI for a snappy experience, while lightweight checks verify that the response stays grounded in the retrieved context and doesn't hallucinate citations.
7. **Logging & Evaluation:** In the background, every turn logs latency, token usage, retrieved chunks, and user feedback (thumbs up/down). I keep a small golden dataset of test questions so whenever I tweak chunk sizes or prompts, I can measure whether accuracy actually improved.



## 3. Vector Databases & Real-World Selection

### What a Vector Database Actually Does
Traditional databases look for exact matches or keyword overlaps if you search for `"damaged stone carving"`, a standard SQL `LIKE` query won't find a document that says `"eroded bas relief sculpture"`. 

A **vector database** solves this by storing data as high-dimensional numerical arrays (**embeddings**) generated by an embedding model. Because texts, images, or audio with similar meanings land close together in that mathematical space, the database uses Approximate Nearest Neighbor (**ANN**) algorithms to find conceptually similar items in milliseconds even when zero exact words match while still letting you filter by traditional metadata (like dates, user IDs, or categories).

### Unique Real-World Use Case: Offline Heritage Site & Museum Audio-Visual Guide (Ajanta & Ellora Caves)

**The Problem:**
Imagine building a multilingual digital storytelling and restoration assistant for visitors exploring historic cave complexes like **Ajanta and Ellora**. Visitors snap a photo of a faded mural or a weathered sculpture on their phone or ask a spoken question in Marathi, Hindi, or English and want to know the Jataka tale behind that exact panel, what the original pigments looked like before erosion, and which nearby cave connects to the same historical dynasty.

Here is why standard search fails here:
1. **No text labels on walls:** A tourist doesn't know the archaeological catalog number; they only have a noisy photo of a partially faded painting or a vague description like *"the panel with the king riding an elephant near the doorway."*
2. **Spotty connectivity inside rock-cut caves:** Deep inside stone caves, mobile internet drops constantly, so the retrieval system needs to run fast, lightweight, and either locally on an edge server at the visitor center or with very low memory overhead.
3. **Multimodal + Metadata filtering:** We need to match both **image embeddings** (visual similarity of the mural) and **text embeddings** (historical notes and restoration logs), while filtering by metadata like `cave_number = 16` or `dynasty = Vakataka`.

**Which Vector Database I Would Choose: Qdrant**

For this problem, I would pick **Qdrant** (specifically running self-hosted via Docker on the local visitor center server, with an option to scale to Qdrant Cloud later).

**Why Qdrant fits this exact problem better than alternatives:**
* **Payload Filtering Built Into the Index:** When a visitor is standing inside *Cave 16*, we shouldn't search across all 30+ caves and risk matching a visually similar carving from Cave 29. Qdrant integrates metadata filtering directly into its HNSW graph traversal rather than filtering *after* the vector search, keeping results both accurate and fast.
* **Named Vectors for Multimodal Data:** Qdrant lets a single record hold multiple distinct vectors—for example, one vector from a vision model (for the restored/original mural image) and another from a text embedding model (for the historical story and conservation notes) so we can query by photo, by text, or combine both cleanly.
* **Lightweight Rust Footprint & Quantization:** Because Qdrant is written in Rust and supports scalar/product quantization out of the box, it runs comfortably on modest on-prem hardware at a heritage site without needing massive RAM—unlike heavier JVM based engines like Milvus or Elasticsearch, and without forcing sensitive unpublished archaeological restoration datasets into a SaaS only tool like Pinecone.
